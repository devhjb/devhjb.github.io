餐饮 POS 打印很容易被低估。

表面看，它只是下单后打一张厨房单，结账后打一张小票。真正接入以后才会发现，打印链路不是一个简单的“调用接口 -> 打印成功”。

它至少同时牵扯到几件事：

- 云端业务系统什么时候生成打印任务。
- 哪台 POS 负责执行本地打印。
- 多台 POS 同时在线时，怎么避免重复出纸。
- POS 拿到任务后没有上报怎么办。
- 打印机发送前失败和发送后无响应，能不能自动重试。
- 扫码单、线上单、当前 POS 退出后，谁来兜底。

这篇文章聊一次餐饮 POS 打印执行模型的设计取舍。

核心结论先放前面：

```text
热敏打印不能承诺物理 exactly-once。

后端真正能治理的是：
任务只被一个执行端有效认领；
执行结果必须可追踪；
发送后结果未知不能自动重试；
需要有主 POS 兜底和人工处理入口。
```

## 1. 问题不是“打印接口调没调”

很多打印问题一开始会被描述成：

```text
下单后厨房没出单
结账小票没打印
打印慢
偶尔重复打
有的档口有小票，有的档口没有
```

如果只站在接口视角，很容易问错问题：

```text
下单接口是不是慢？
后端是不是没生成打印任务？
POS 是不是没调打印接口？
```

这些问题当然要查，但它们不是完整模型。

餐饮打印的真实链路更像这样：

```text
业务动作成功
  -> 云端按路由生成打印任务
  -> POS 拉取待打印任务
  -> 云端把任务从 PENDING claim 到 PRINTING
  -> POS 本地连接热敏打印机
  -> POS 发送 ESC/POS / 驱动指令
  -> POS 上报 SUCCESS / FAILED / UNCERTAIN
  -> 云端归档或进入人工处理
```

任意一段断了，用户看到的都是“没打印”。

所以这类问题不能只看业务接口成功，也不能只看数据库里有没有任务。必须把打印看成一个“云端任务 + 本地执行 + 状态闭环”的执行系统。

## 2. 为什么热敏打印不是 exactly-once

很多后端系统喜欢追求 exactly-once。

但热敏打印这里要先承认一个事实：物理世界不是数据库事务。

当 POS 往局域网打印机写 socket 时，可能出现几种情况：

| 现象 | 后端是否能确定是否出纸 |
| --- | --- |
| 连接打印机前失败 | 能，基本没出纸 |
| 还没写入任何字节就失败 | 能，基本没出纸 |
| 写入一半后断开 | 不能，可能出了半张 |
| 全部写入成功但无响应 | 不能，可能已出纸 |
| 打印机卡纸、缺纸、缓存异常 | 不一定能准确知道 |
| POS 写成功但上报失败 | 云端不知道本地真实结果 |

这里最危险的是“发送后失败”。

如果系统看到失败就自动重试，用户可能拿到两张小票，厨房可能收到两张重复出餐单。

在餐饮场景里，重复出纸不只是纸张浪费，它可能导致：

- 厨房重复备菜。
- 服务员重复上菜。
- 收银员误以为结账小票未出。
- 顾客拿到多张凭证。
- 后台任务状态和现场事实不一致。

所以设计上不能假装打印是 exactly-once。

更务实的目标是：

```text
发送前失败，可以重试；
发送后失败，不自动重试；
发送后结果未知，进入 UNCERTAIN；
人工确认后再决定已打印、补打或取消。
```

## 3. 执行模型：即时执行 + 主 POS 兜底

餐饮门店里通常不止一台 POS。

如果强行规定“只有主 POS 能打印”，会带来两个问题：

第一，当前下单 POS 明明能访问门店打印机，却还要等主 POS 后台轮询，用户体感变慢。

第二，如果主 POS 没开、网络闪断或执行器异常，当前业务产生的打印任务会一直等。

所以更合理的模型是：

```text
下单 / 结算 POS：优先即时执行当前业务批次
主 POS：后台短轮询兜底全门店遗留任务
云端：统一生成任务、认领任务、校验结果上报
```

![餐饮 POS 打印执行模型](/assets/posts/pos-print-execution/execution-model.png)

这套模型里有两个执行入口。

### 3.1 即时执行

业务 POS 下单、预结、结账成功后，后端如果生成了打印任务，会把本次业务动作对应的 `printBatchNo` 返回给 POS。

POS 拿到批次号后，立即拉取当前批次任务：

```text
pull-pending(
  executorMode = IMMEDIATE,
  hostDeviceId = 当前 POS 设备,
  printBatchNo = 本次业务返回的批次号
)
```

即时执行必须带 `printBatchNo`。

这是关键边界。它保证当前 POS 只认领自己刚刚产生的这批任务，不会顺手把门店里其它待打印任务抢走。

### 3.2 主 POS 后台兜底

主 POS 或常驻打印执行器负责兜底：

```text
pull-pending(
  executorMode = BACKGROUND,
  hostDeviceId = 主 POS 设备
)
```

后台兜底不传 `printBatchNo`，按门店 FIFO 拉取遗留 `PENDING` 任务。

它解决的是：

- 扫码下单，没有明确的下单 POS。
- 线上单，没有本地执行端。
- 下单 POS 退出或崩溃。
- 即时执行漏拉、漏打、漏上报。
- 发送前失败后重新进入队列的任务。

即时执行负责体验，主 POS 兜底负责可靠性。

### 3.3 两条路径共用同一套 Claim

即时执行和后台兜底不能各自写一套逻辑。

它们必须共享同一套认领状态机：

```text
PENDING -> PRINTING
```

只有成功从 `PENDING` 更新到 `PRINTING` 的执行端，才拿到本次有效的 `claimToken`。

这样下单 POS 和主 POS 同时拉同一批任务时，也只有一个会成功。

## 4. printBatchNo、jobNo、claimToken 各自是什么

打印链路里最容易混的字段有三个。

### 4.1 printBatchNo：一次业务动作的批次号

一次点菜、一次预结、一次结账，可能生成多条打印任务。

例如三档口三道菜：

```text
档口 A 后厨总单
档口 B 后厨总单
档口 C 后厨总单
顾客账单
菜品级分单
```

这些任务可以属于同一个业务打印批次。

`printBatchNo` 的作用是：

```text
告诉即时执行的 POS：
你这次只拉当前业务动作产生的这批任务。
```

它不是单条任务编号，也不是上报结果用的主键。

### 4.2 jobNo：单条打印任务号

`jobNo` 才是单条打印任务。

一次 `pull-pending` 可能返回多个 job。POS 必须遍历每一个 job：

```text
for each job:
  打印 job
  上报 jobNo + claimToken + status
```

如果 POS 只处理返回数组的第一条，就会出现典型问题：

```text
后端生成了 6 个 job
POS 一次 claim 了 6 个 job
POS 只打印并上报第 1 个
剩余 5 个一直 PRINTING
租约超时后进入 UNCERTAIN
```

这种问题从用户视角看是“有些档口没出单”，但后端证据会显示：任务已经被 POS 拿走，只是 POS 没闭环处理完整数组。

### 4.3 claimToken：本次认领令牌

`claimToken` 不是装饰字段。

它的作用是：

```text
证明这次上报来自当前有效认领者。
```

结果上报必须带：

```text
jobNo
hostDeviceId
claimToken
status
failureStage
```

后端更新结果时要校验：

```text
merchantId 匹配
jobNo 匹配
status = PRINTING
claimToken 匹配当前任务
lease 未过期或满足幂等处理规则
```

错误 token、过期 token、非 `PRINTING` 状态，都不能覆盖终态。

这是防止重复上报、延迟上报、旧 POS 重放请求把任务状态改坏的底线。

## 5. 状态机：PENDING -> PRINTING -> SUCCESS / UNCERTAIN

打印任务状态机不要设计得过于乐观。

一条任务至少需要这些状态：

![打印任务状态机与结果未知治理](/assets/posts/pos-print-execution/state-machine.png)

### 5.1 PENDING

任务已生成，等待执行端认领。

来源可能是：

- 下单生成厨房单。
- 预结生成账单。
- 结账生成小票。
- 人工补打生成新任务。
- 发送前失败后回到队列。

`PENDING` 可以被 claim。

### 5.2 PRINTING

任务已被某个执行端认领。

进入 `PRINTING` 时，需要记录：

- 执行设备。
- `claimToken`。
- `leaseUntil`。
- 尝试次数。
- 派发时间。

`PRINTING` 不是成功，它只是“有人拿走任务准备执行”。

### 5.3 SUCCESS

执行端明确上报成功。

这时任务进入终态。

重复上报同一个成功结果，可以按幂等处理；但不能允许另一个旧 token 把它改回失败或待打印。

### 5.4 FAILED

这里要小心。

失败不是一个语义。

应该至少区分：

```text
BEFORE_SEND：发送前失败
AFTER_SEND：发送后失败或无响应
```

`BEFORE_SEND` 代表还没真正把指令发给打印机。例如：

- 找不到打印机。
- 连接失败。
- 端口不可达。
- 驱动不可用。

这类失败通常可以按重试策略回到 `PENDING`，由即时 POS 或主 POS 后台继续处理。

`AFTER_SEND` 不能这么做。

### 5.5 UNCERTAIN

`UNCERTAIN` 表示结果未知。

典型来源：

- 已经开始写 socket，但中途异常。
- 写入成功，但打印机没有明确响应。
- 打印机状态不可判断。
- POS 已 claim 任务，但租约内没有上报。
- POS 可能已经出纸，但网络或程序在上报前失败。

`UNCERTAIN` 的含义不是失败，而是：

```text
系统无法证明没有出纸。
```

因此它不能自动回到 `PENDING`。

否则就会把“结果未知”变成“自动重打”，重复打印风险直接放大。

## 6. AFTER_SEND 为什么不能自动重试

这是整篇最关键的取舍。

对于业务系统来说，失败后重试是常规手段。但打印不是普通 RPC。

普通 RPC 重试的前提是：服务端可以通过幂等键控制副作用。

热敏打印的副作用发生在纸上。

一旦字节已经送到打印机，后端没有办法可靠撤销，也无法通过数据库锁证明“绝对没出纸”。

所以 `AFTER_SEND` 后自动重试，等价于赌现场没有出纸。

这个赌注不值得。

更稳的策略是：

```text
AFTER_SEND -> UNCERTAIN
UNCERTAIN -> 人工确认
人工确认：
  - 已出纸：标记 SUCCESS
  - 未出纸：补打新任务
  - 不需要了：取消
```

这看起来比自动重试麻烦，但它把风险显式暴露给人，而不是让系统偷偷重复出纸。

## 7. 租约超时也不应该直接回 PENDING

另一个容易犯的错是：

```text
PRINTING 超时未上报 -> 自动回 PENDING
```

这同样危险。

因为任务已经被 POS 拿走了。POS 可能已经打印成功，只是没来得及上报；也可能正在卡顿；也可能已经发送给打印机但程序崩了。

此时如果主 POS 后台把它重新拉走再打一次，就可能重复出纸。

更合理的是：

```text
PRINTING 超过 leaseUntil
  -> 标记 UNCERTAIN
  -> 不自动重试
  -> 打印任务中心提示人工确认
```

租约不是“重打定时器”，而是“认领结果迟迟没闭环，需要暴露风险”的时间边界。

## 8. 业务成功和打印成功必须解耦

下单成功不应该因为打印失败而回滚。

结账成功也不应该因为小票没出而回滚。

交接班记录生成成功，也不应该因为当前 POS 没拉取任务而阻塞退出。

原因很简单：

```text
业务事实已经发生；
打印只是现场凭证或执行通知。
```

如果把业务事务和物理打印绑死，系统会陷入更糟糕的状态：

- 菜已经下了，但因为打印失败回滚订单。
- 钱已经收了，但因为小票失败让付款状态不确定。
- 交班已完成，但收银员无法退出。

正确做法是：

```text
业务链路负责业务状态；
打印链路负责打印任务状态；
两者通过 printBatchNo / sourceBizId 关联；
打印失败进入任务治理，不反向污染业务事实。
```

前端提示也要跟着这个口径走：

```text
业务成功，打印结果未知，请检查是否出纸。
```

而不是：

```text
提交失败。
```

## 9. 主 POS 兜底解决什么，不解决什么

主 POS 后台兜底很重要，但它不是万能补偿器。

它适合处理：

- 没有明确业务 POS 的任务。
- 业务 POS 没有即时拉取。
- 发送前失败后重新进入队列的任务。
- 门店内遗留 `PENDING` 任务。

它不应该自动处理：

- 已经 `PRINTING` 且还没超时的任务。
- `AFTER_SEND` 进入 `UNCERTAIN` 的任务。
- 租约超时但结果未知的任务。

主 POS 的角色是“兜底执行待打印任务”，不是“把所有不确定状态重打一遍”。

## 10. 任务中心应该怎么展示

如果系统有打印任务中心，状态文案要让用户理解风险。

可以这样设计：

| 状态 | 展示建议 | 操作 |
| --- | --- | --- |
| `PENDING` | 待打印 | 可取消 |
| `PRINTING` | 执行中 | 等待上报或超时 |
| `SUCCESS` | 已打印 | 可补打 |
| `FAILED` | 打印失败 | 可补打 / 取消 |
| `UNCERTAIN` | 结果未知，请确认是否出纸 | 确认已打印 / 补打 / 取消 |
| `CANCELLED` | 已取消 | 查看记录 |

`UNCERTAIN` 的产品文案一定要谨慎。

不要写：

```text
打印失败，系统将自动重试
```

更准确的是：

```text
打印结果未知，可能已经出纸，请人工确认。
```

这能让现场人员按真实情况处理，而不是被系统误导。

## 11. 排查打印问题时看什么证据

打印问题排查要分两类证据。

### 11.1 数据库证据

数据库适合证明：

- 业务单据是否创建。
- 打印任务是否生成。
- 一次业务动作生成了多少 job。
- job 当前是什么状态。
- 是否有同一个 `printBatchNo`。
- 是否被同一个 `claimToken` 认领。
- 是否超过租约变成 `UNCERTAIN`。

典型判断：

```text
同一 printBatchNo 下有 6 个 job
同一 claimToken
同一 executorDevice
1 个 SUCCESS
5 个 UNCERTAIN
```

这说明：

```text
后端生成了 6 个任务；
POS 一次拉取认领了 6 个任务；
不是多设备抢占；
不是后端只返回 1 个；
问题更可能在 POS 只处理或只上报了第一条。
```

### 11.2 网关日志证据

网关日志适合证明：

- 下单接口耗时。
- `pull-pending` 耗时。
- POS 是否调用了结果上报。
- 请求体里有没有目标 `jobNo`。
- 前端到底有没有发出剩余 job 的上报请求。

不要用数据库时间直接推断接口慢。

数据库能证明对象什么时候落库，不能证明 HTTP 请求耗时。接口耗时要看 access log、应用日志或链路追踪。

## 12. 常见坑

### 12.1 只处理 pull-pending 返回的第一条

这是多档口打印里很典型的问题。

后端返回的是 job 数组，不是单条任务。

POS 必须遍历全部 job。每条都要打印，每条都要上报。

### 12.2 把 hostDeviceId 当成 printerId

`hostDeviceId` 是执行打印的 POS 设备，不是目标打印机。

目标打印机信息由任务返回，包括打印机 ID、连接方式、IP、端口、驱动、纸宽、模板快照等。

### 12.3 用 printBatchNo 上报结果

`printBatchNo` 只用于即时拉取当前业务批次。

上报结果必须用单条任务的 `jobNo + claimToken`。

### 12.4 拉到任务后不上报

POS 拉到任务后，如果本地打印执行完成但不上报，任务会一直停在 `PRINTING`，最后进入 `UNCERTAIN`。

这会让后端无法知道现场真实结果。

### 12.5 AFTER_SEND 自动重试

这是重复出纸的主要来源。

发送后无响应不能自动重试，应进入 `UNCERTAIN`。

### 12.6 把 ESC/POS 指令当字符串处理

如果后端返回的是 Base64 编码的 ESC/POS 字节，POS 端应直接解码为 Buffer 写入打印机。

不要把它先转字符串，再用 UTF-8、GB18030 或 TextEncoder 重编码。热敏小票里可能有光栅位图指令，字节流被字符串链路处理后很容易乱码或废纸。

这块更偏渲染和设备适配，可以单独再写一篇。

## 13. 这套模型的底线

最终这套打印执行模型的底线可以概括成六句话。

```text
1. 业务成功不等于打印成功。
2. 打印任务必须显式建模。
3. 执行端必须先 claim，再打印。
4. 上报结果必须带 claimToken。
5. BEFORE_SEND 可以重试，AFTER_SEND 只能进入 UNCERTAIN。
6. 主 POS 兜底 PENDING，不兜底“可能已经出纸”的不确定状态。
```

这套设计不能让热敏打印变成物理 exactly-once。

但它能做到三件更现实的事：

- 减少重复打印。
- 让漏打、未上报、结果未知有状态可查。
- 让人工补打和确认建立在可解释的任务记录上。

对餐饮 POS 来说，这比假装“失败就自动重试一定没问题”要可靠得多。
